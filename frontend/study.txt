
[AI 차량 예지 정비 시스템 - 발표 가이드]

================================================================================
1. 프로젝트 개요
================================================================================

**프로젝트명**: AI 차량 예지 정비 시스템 (AI-5)
**핵심 가치**: 차량의 미래를 예측하고, 고장을 사전에 방지

**주요 기능**
1. OBD-II 기반 실시간 차량 데이터 수집 및 주행 분석
2. AI 멀티모달 진단 (Vision, Audio, 시계열 데이터)
3. 소모품 수명 예측 및 자동 교체 알림
4. RAG 기반 차량 매뉴얼 챗봇
5. 주행 안전 점수 산출 및 피드백

**시스템 구성**
```
┌─────────────┐         ┌──────────────┐        ┌─────────────┐
│   Mobile    │◄───────►│   Backend    │◄──────►│  AI Server  │
│  (React     │  HTTPS  │ (Spring Boot)│  REST  │  (FastAPI)  │
│   Native)   │  +JWT   │              │        │             │
└─────────────┘         └──────────────┘        └─────────────┘
      ▲                        ▲                      ▲
      │                        │                      │
      │                        ▼                      │
  OBD-II              ┌──────────────┐                │
  Bluetooth           │  PostgreSQL  │                │
                      │   +pgvector  │                │
                      │  TimescaleDB │                │
                      └──────────────┘                │
                              ▲                       │
                              │                       │
                              └───────────────────────┘
                                  Vector Search
```

**기술 철학**
- **Hybrid AI**: 로컬 모델(속도) + 클라우드 LLM(정확도)
- **Offline-First**: 네트워크 단절에도 데이터 유실 방지
- **Cost-Efficient**: Router 모델로 불필요한 API 호출 필터링

2. 핵심 데이터 플로우
================================================================================

**[주행 데이터 수집 → 분석 → 알림]**

1. 앱 실행 시 OBD 자동 연결 → Bluetooth 스캔 및 페어링
2. Foreground Service가 Speed > 0 감지 시 자동 주행 시작
3. 1초 간격 데이터 수집 (Speed, RPM, Coolant, Load 등)
4. 주행 종료 (Speed = 0 && RPM = 0이 10분 지속)
   → 주행 통계 계산 (평균 속도, 안전 점수, 급가속 횟수 등)
   → 소모품 마모 가중치 업데이트
   → 잔존 수명 < 30% 시 FCM 푸시 알림

**[멀티모달 AI 진단]**

**Vision (시각 진단)**
1. 사용자가 엔진룸/계기판 촬영
2. YOLOv11m-CLS → 장면 분류 (4종: 엔진룸/계기판/외관/타이어)
3. YOLOv11 Specialist → 부품 탐지 (배터리, 오일캡 등 50종+)
4. GPT-4o Vision → 결함 해석 ("오일 누유 의심", "벨트 균열")

**Audio (청각 진단)**
1. 사용자가 엔진 소음 녹음
2. Mel-Spectrogram 변환 → AST Model 분류
3. 이상음 탐지 (노킹, 벨트 소음 등)
4. GPT-4o로 2차 해석 및 권고사항 제시

**RAG 챗봇**
1. 사용자 질문 → Embedding 벡터 변환
2. pgvector로 차량 매뉴얼 검색 (메타데이터 필터링)
3. 검색된 컨텍스트 + 질문 → GPT-4o 답변 생성
4. 할루시네이션 방지 (검색된 매뉴얼 기반 답변)

3. AI 모델
================================================================================

**A. Vision (시각 진단)**
- YOLOv11m-CLS: 장면 분류 (모바일 최적화)

**B. Audio (청각 진단)**
- AST (Audio Spectrogram Transformer): 이상음 분류
- GPT-4o: 음성 데이터 해석 및 2차 소견

**C. RAG (검색 증강 생성)**
- Embedding: OpenAI text-embedding-3-small
- Vector DB: pgvector (PostgreSQL 확장)
- LLM: GPT-4o (Streaming 응답)

4. 기술 스택

A. Frontend (Mobile App - React Native)
--------------------------------------------------------------------------------
- **React Native 0.81 + Expo SDK 54**
  - 선정 이유: 크로스 플랫폼 개발로 iOS/Android 동시 지원, 빠른 개발 속도
  - Hot Reload로 즉각적인 피드백, Native 모듈과의 확장성 결합

- **TypeScript 5.x**
  - Strict Type Checking으로 런타임 에러 사전 차단
  - 대규모 코드베이스에서도 안전한 리팩토링 가능

- **Zustand (상태 관리)**
  - 선정 이유: Redux 대비 경량화, OBD 센서 데이터처럼 고빈도 업데이트에 최적화
  - 단방향 데이터 흐름으로 예측 가능한 상태 관리
  - 주요 Store: useVehicleStore, useObdStore, useAiDiagnosisStore

- **Offline-First Architecture**
  - AsyncStorage 로컬 저장 → 네트워크 복구 시 자동 동기화
  - 타임스탬프 기반 충돌 해결 로직

- **Dual-Mode Bluetooth**
  - BLE Manager: 최신 BLE 4.0+ OBD 스캐너 (저전력 모드)
  - Bluetooth Classic: 구형 ELM327 호환 (SPP 프로토콜)
  - 우선순위 큐: 주행 시작/종료 명령 최우선 처리

- **Multimedia Processing**
  - expo-camera: 이미지 quality 0.8 압축, EXIF 메타데이터 기록
  - expo-av: 48kHz HIGH_QUALITY 샘플링, 실시간 파형 시각화

- **Foreground Service**
  - Android Foreground Service로 OS 종료 방지
  - Doze 모드에서도 데이터 수집 보장

- **Axios Interceptors**
  - Request: JWT Access Token 자동 헤더 추가
  - Response: 401 시 Refresh Token으로 자동 재발급, 네트워크 에러 시 재시도 (최대 3회)


B. Backend (API Server - Spring Boot)
--------------------------------------------------------------------------------
- **Spring Boot 3.5.9 (Java 17 LTS)**
  - 선정 이유: 엔터프라이즈급 안정성, 대규모 트래픽 처리 검증됨
  - Auto-Configuration으로 빠른 개발, Embedded Tomcat으로 독립 실행

- **Java 17 LTS Features**
  - Records: DTO 보일러플레이트 제거
  - Pattern Matching: instanceof 체크와 캐스팅 동시 처리
  - Sealed Classes: 타입 안전성 강화

- **Spring Data JPA + QueryDSL**
  - JPA: Repository 인터페이스만 정의하면 CRUD 자동 구현
  - QueryDSL: 컴파일 타임 타입 체크 가능한 동적 쿼리 빌더
  - @EntityGraph로 N+1 문제 방지

- **PostgreSQL + TimescaleDB**
  - 시계열 데이터 최적화: OBD 로그(초당 수백만 건) 효율 저장
  - Hypertable: 시간 기반 자동 파티셔닝
  - Continuous Aggregates: 일/주/월별 통계 자동 계산

- **Spring Security + JWT**
  - Stateless 인증으로 확장성 확보
  - Access Token 15분 / Refresh Token 7일
  - Token Rotation으로 보안 강화

- **BCrypt Password Hashing**
  - Salt 자동 추가로 Rainbow Table 공격 방지
  - Work Factor로 미래 컴퓨팅 파워 증가 대응

- **RabbitMQ**
  - AI 분석 같은 무거운 작업 비동기 처리
  - Message Durability + Dead Letter Queue로 신뢰성 확보

- **AWS S3 + Firebase FCM**
  - S3 Presigned URL로 미디어 파일 보안 접근
  - FCM으로 소모품 알림, 진단 완료 알림 실시간 전송

- **Testing**
  - JUnit 5 (Parameterized Tests, Nested Tests)
  - MockMvc (통합 테스트)
  - Test Containers (실제 PostgreSQL 컨테이너 사용)


C. AI (Inference Engine - FastAPI)
--------------------------------------------------------------------------------
- **FastAPI (Python 3.10+)**
  - 선정 이유: AI/ML 라이브러리 풍부, 비동기 I/O로 동시 요청 효율 처리
  - ASGI (uvicorn): WSGI 대비 10배 빠른 속도

  - TorchScript로 모델 최적화 (메모리 절약)

- **Ultralytics YOLOv11**
  - SOTA 실시간 객체 탐지 (정확도 + 속도)
  - 커스텀 데이터셋으로 파인튜닝
  - ONNX 포맷 변환으로 다양한 플랫폼 배포

- **OpenCV + Librosa**
  - OpenCV: 고속 이미지 전처리 (Resize, Crop, Contour Analysis)
  - Librosa: Mel-Spectrogram 변환, MFCC 특징 추출

- **HuggingFace Transformers (AST)**
  - Audio Spectrogram Transformer
  - Attention Mechanism으로 중요 주파수 대역 자동 포커싱

  - Async Client로 비동기 API 호출

  - pgvector: HNSW 인덱스로 밀리초 내 벡터 검색
  - Metadata Filtering으로 사용자 차량 모델 매뉴얼만 검색

- **Infrastructure**
  - Singleton Pattern: AI 모델 서버 시작 시 1회만 로드
  - Lazy Loading: AST 모델 첫 요청 시 로드 (메모리 절약)
  - Redis 캐싱: 동일 요청 시 캐싱 결과 반환 (TTL 24시간)
  - ELM327 Emulator: 가상 차량 시뮬레이터로 다양한 시나리오 테스트

5. 핵심 기능 상세
================================================================================

**A. OBD-II 실시간 모니터링**
- ELM327 통신 프로토콜 지원 (AT/PID 명령)
- Foreground Service로 백그라운드 수집 보장

- Auto Trip: 주행 시작/종료 자동 감지

**B. 소모품 수명 예측**
- Wear Factor 개념: 주행 패턴 기반 마모 가중치
- 증분 수명 차감: (주행 거리 × 마모계수 / 전체 수명) × 100
- 잔존 수명 < 30% 시 FCM 알림
- 대상 소모품: 엔진오일, 배터리, 냉각수, 브레이크패드 등 10종+

**C. 주행 안전 점수**
- 100점 만점 감점 방식
- 급가속(0.3g 이상), 급감속(-0.4g 이하) 1회당 -2점
- 과속(제한속도 초과), 공회전 시간 반영
- 주행 이력 기반 평균 점수 산출

**D. AI 진단**
- 자동 트리거: 주행 거리 >= 1km
- LSTM 모델: 시계열 이상 패턴 탐지
- GPT-4o: DTC 코드 해석 및 조치 권고
- 수동 트리거: 사용자 요청 시 즉시 진단

8. 예상 Q&A (1차 방어 기제 - 기능 중심)
================================================================================

Q1. OBD 연결이 끊기면 주행 데이터는 어떻게 되나요?
A: 앱 내부의 로컬 저장소(AsyncStorage)와 우선순위 큐(Priority Queue)에 데이터를 임시 버퍼링합니다. 네트워크나 블루투스가 일시적으로 끊겨도 데이터는 유실되지 않으며, 재연결 시 백그라운드 서비스가 자동으로 서버에 전송하여 데이터 정합성을 보장합니다.

Q2. 왜 Router 모델(MobileNet)을 따로 쓰나요? 처음부터 GPT-4o를 쓰면 더 정확하지 않나요?
A: 비용과 속도 최적화 때문입니다.
모든 이미지를 GPT-4o로 보내면 비용이 많이 들고 응답 속도가 느립니다(약 3~5초).
반면 MobileNet은 무료이며 0.1초 이내에 처리가 가능합니다. 단순한 장면 분류는 로컬 모델이 빠르게 처리하고, 복잡한 추론/진단이 필요한 경우에만 고성능 모델(GPT/YOLO)을 호출하여 효율성을 극대화했습니다.

Q3. RAG(검색 증강 생성)가 구체적으로 어떤 역할을 하나요? 왜 필요한가요?
A: 일반적인 LLM은 훈련되지 않은 최신 정보나 특정 차량의 제원을 알지 못해 잘못된 정보를 지어내는 '할루시네이션(Hallucination)' 문제가 발생할 수 있습니다.
저희 시스템은 RAG를 통해 Vector DB에 저장된 해당 차량(예: 아반떼 CN7, 쏘렌토 MQ4)의 공식 취급 설명서를 먼저 검색하고, 그 내용을 근거(Grounding)로 답변을 생성하므로 신뢰할 수 있는 정보를 제공합니다.

Q4. 하이브리드 AI라고 하셨는데, 구체적으로 어디서 어떻게 동작하나요?
A:
1. 온디바이스/로컬 (Fast): OBD 데이터 수집, 기본적인 이미지 장면 분류(MobileNet) 등 즉각적인 반응이 필요한 작업.
2. 클라우드 (Deep): 정밀 부품 인식(YOLO), 고장 원인 추론(GPT-4o), 매뉴얼 검색(RAG) 등 고성능 연산이 필요한 작업.
이 둘을 유기적으로 배분하여 모바일 기기의 배터리/리소스를 절약하면서도 전문가 수준의 진단 서비스를 제공합니다.

Q5. 실시간 안전 운전 점수는 어떻게 산출되나요?
A: 주행 중 1초 단위로 수집된 속도(Speed), RPM, 급가속/급감속(G-Force) 데이터를 기반으로 합니다. 주행이 종료되면 이 시계열 데이터를 백엔드 서버가 분석하여 위험 운전 빈도를 계산하고, 이를 100점 만점의 안전 점수로 환산하여 사용자에게 피드백을 제공합니다.

Q6. 모든 차종에서 사용 가능한가요?
A: 네, 2008년 이후 출시된 모든 가솔린/디젤 차량은 표준 OBD-II 프로토콜을 의무 지원하므로 사용 가능합니다. 다만, 전기차(EV)의 경우 배터리 전용 PID가 필요하여 현재는 호환성 테스트 중입니다.

Q7. 진단의 정확도는 얼마나 되나요?
A: 자체 테스트 결과, 시각 진단(Vision)은 95% 이상, 청각 진단(Audio)은 90% 이상의 분류 정확도를 보였습니다. 특히 RAG를 도입한 후, 챗봇 답변의 기술적 정확도가 기존 LLM 대비 40% 이상 향상되었습니다.

9. 기술 면접 예상 질문 (2차 방어 기제 - 비즈니스/아키텍처 중심)
================================================================================

Q8. Scalability (확장성): 사용자가 10만 명으로 늘어나면 백엔드 부하를 어떻게 감당할 것인가?
A: 현재 AI 서버와 백엔드 서버(Spring Boot)가 분리된 MSA 지향 구조입니다.
- AI 서버: 연산량이 많은 추론 작업은 별도의 FastAPI 서버가 전담하며, 필요 시 Kubernetes 등으로 수평 확장(Scale-out)이 용이합니다.
- 비동기 처리: 주행 데이터 분석과 같이 무거운 작업은 즉시 처리하지 않고, RabbitMQ와 같은 메시지 큐 시스템을 도입할 수 있도록 서비스 레이어가 분리되어 있습니다.

Q9. Cost Efficiency (비용 효율성): GPT-4o API 비용이 만만치 않을 텐데, 수익 모델이나 비용 절감 전략이 있는가?
A: 무조건적인 API 호출을 지양하고 있습니다.
1. 필터링: Router 모델이 1차로 "유의미한 차량 이미지"인지 검증한 후에만 GPT를 호출합니다. (쓰레기 데이터 배제)
2. 캐싱: 동일한 DTC 코드나 자주 묻는 질문에 대한 답변은 Redis 등에 캐싱할 수 있도록 설계했습니다.
3. 학습 데이터화: 장기적으로는 GPT가 생성한 양질의 답변을 데이터셋으로 축적하여, 더 저렴한 소형 모델(Llama 3 등)을 파인튜닝(Fine-tunning)해 대체할 계획입니다.

Q10. Reliability (신뢰성): 지하주차장 등 네트워크 음영 지역에서는 어떻게 동작하는가?
A: 본 서비스의 핵심인 '데이터 수집'은 네트워크 상태와 무관하게 동작합니다.
앱 내부의 SQLite(또는 로컬 스토리지)에 데이터를 우선 저장하고, 네트워크가 복구(Online)되는 즉시 백그라운드에서 서버와 동기화(Sync)하는 Offline-First 설계를 따르고 있습니다. 따라서 주행 기록이 유실될 염려는 없습니다.

Q11. Security (보안): 사용자 주행 데이터나 음성 정보는 민감한데, 보안 대책은?
A: 모든 통신은 HTTPS(TLS) 암호화 통신을 사용합니다.
또한, 사용자가 업로드한 이미지와 오디오 파일은 퍼블릭 접근이 차단된 AWS S3 Private Bucket에 저장되며, 접근 권한이 있는 서버(Pre-signed URL)를 통해서만 일시적으로 접근 가능하도록 설계하여 데이터 유출을 방지하고 있습니다.

Q12. Technical Depth (심화): 왜 검색엔진(Elasticsearch)이 아니라 Vector DB를 썼나요?
A: 차량 증상에 대한 질문은 "엔진에서 끽끽 소리가 나요"처럼 비정형적이고 의미적인 검색이 필요하기 때문입니다.
단순 키워드 매칭(Elasticsearch)은 문맥을 파악하지 못해 정확도가 떨어집니다. 반면 Vector DB(pgvector)는 문장의 의미적 유사성(Semantic Similarity)을 기반으로 검색하므로, 사용자가 "심장이 뛰는 것 같은 소리"라고 표현해도 "엔진 노킹(Knocking)" 관련 매뉴얼을 찾아줄 수 있습니다.

Q13. Performance (성능): 모바일 앱의 배터리 소모 최적화 전략은 무엇인가요?
A: 
1. 가변적 데이터 수집 주기: 가속도 센서(Accelerometer)를 활용하여 정차 중일 때는 데이터 수집 주기를 늦추고, 주행 중에만 1초 단위로 수집합니다.
2. 미디어 압축 전송: 카메라 이미지는 quality: 0.8로 압축하고, 오디오 파일도 모노 채널로 변환하여 업로드 데이터 양을 최소화, 통신 모듈(LTE/5G) 사용 시간을 줄였습니다.

Q14. Architecture (아키텍처): RabbitMQ 메시지가 유실되면 어떻게 하나요?
A: 메시지 신뢰성(Reliability)을 위해 Producer Confirms와 Consumer Acknowledgement(Ack)를 활성화했습니다.
또한, 큐(Queue)와 메시지를 Durable 모드로 설정하여 브로커가 재시작되더라도 디스크에 저장된 메시지가 보존되도록 구성했습니다.

Q15. AI Optimization (AI 최적화): 실시간 추론 시 Latency(지연 시간) 문제는 없었나요?
A: 순수 Python(Sync) 코드로 작성하면 병목이 발생하지만, FastAPI의 async/await 비동기 처리를 통해 I/O 바운드 작업(DB 조회, 외부 API 호출)을 병렬로 처리했습니다.
CPU 바운드 작업(이미지 전처리 등)은 별도의 ThreadPoolExecutor나 Celery 워커로 분리할 예정입니다.

Q16. Database (데이터베이스): TimescaleDB와 같은 시계열 DB 관련 고려 사항은?
A: 현재는 PostgreSQL 표준 테이블을 사용하지만, OBD 로그 데이터가 월 수백만 건 이상 쌓일 경우 파티셔닝(Partitioning)과 압축(Compression)이 필수적입니다.
향후 TimescaleDB 확장을 도입하여 시간 기반 쿼리 성능을 최적화하고, 오래된 데이터는 S3 Glacier로 아카이빙하는 수명 주기 정책(Retention Policy)을 수립했습니다.

Q17. DevOps (데브옵스): CI/CD 및 배포 전략은?
A: 현재는 GitHub Actions를 통해 빌드 및 테스트 자동화를 구축 중입니다. 
Blue-Green 배포 전략을 통해 신규 버전 배포 시 다운타임(무중단 배포)을 최소화하고, 문제 발생 시 즉시 롤백할 수 있는 체계를 갖추는 것이 목표입니다.

Q18. Frontend Tech (프론트엔드): 상태 관리 라이브러리로 왜 Redux가 아닌 Zustand를 선택했나요?
A: OBD 데이터와 같이 빈번하게 업데이트되는 스트림을 처리하기에는 Redux의 보일러플레이트가 너무 무겁다고 판단했습니다.
Zustand는 가볍고 훅(Hook) 기반으로 직관적이며, 특히 불필요한 리렌더링을 제어하기 쉬워 고빈도 센서 데이터 처리에 최적이라고 생각했습니다.

9. 발표 핵심 포인트 (Q&A 대비)

**Q1. 왜 이 프로젝트를 선택했나요?**
A: 차량 정비는 전문가 의존도가 높고 비용 부담이 큽니다. AI로 사전 진단하면 사용자는 정비소 방문 전 문제를 파악하고, 정비소는 효율적인 정비 계획을 수립할 수 있습니다.

**Q2. RAG를 왜 사용했나요?**
A: 일반 LLM은 차량 정보를 모르거나 잘못된 정보를 생성합니다. RAG는 차량 매뉴얼을 검색 후 답변하므로 신뢰도가 높습니다.

**Q3. 하이브리드 AI의 장점은?**
A: 로컬 모델로 즉각 반응 + 클라우드 LLM으로 정밀 분석. 모바일 리소스 절약과 전문가 수준 진단을 동시에 달성합니다.

**Q4. 확장성은?**
A: MSA 지향 구조 (AI 서버 분리), RabbitMQ 비동기 처리, Kubernetes 수평 확장 가능

**Q5. 비용 절감 전략?**
A: Router 모델 필터링, Redis 캐싱, 향후 소형 모델 파인튜닝 계획

**Q6. 보안은?**
A: HTTPS(TLS) 암호화, AWS S3 Private Bucket, Pre-signed URL, JWT 토큰 인증

**Q7. 모든 차종 지원?**
A: 2008년 이후 모든 가솔린/디젤 차량 (OBD-II 표준). 전기차는 호환성 테스트 중
