# 시스템 하드코딩 조사 결과 및 개선 계획

본 문서는 서비스의 유지보수성과 유연성을 높이기 위해 현재 시스템(백엔드 및 AI 서버)에 존재하는 하드코딩된 값들과 제약 사항을 조사하고, 이에 대한 개선 방향을 정리한 문서입니다.

## 1. 하드코딩 및 제약 사항 조사 결과

### 1.1 차계부 OCR (ReceiptAnalyzerService)
- **소모품 리스트 제한**: GPT 프롬프트 내에 5가지 핵심 소모품(`ENGINE_OIL, TIRES, BRAKE_PADS, WIPER, BATTERY`)만 명시되어 있어, "부동액", "미션오일" 등 다른 항목은 모두 `UNKNOWN`으로 처리됩니다.
- **모델명 고정**: OpenAI 모델명이 `gpt-4o-mini`로 코드에 직접 작성되어 있습니다.
- **결측치 처리**: 날짜나 주행거리가 영수증에 없을 경우 무조건 오늘 날짜나 차량의 현재 주행거리를 기본값으로 사용합니다.

### 1.2 AI 통합 진단 서비스 (AiDiagnosisService)
- **리소스 제어(세마포어)**: 글로벌 요청 제한(6개) 및 사용자 세션별 제한(3개)이 코드 내 상수로 정의되어 있어 서버 사양 변경 시 대응이 어렵습니다.
- **타임아웃 설정**: 분석 파이프라인의 전체 타임아웃이 600초(10분)로 고정되어 있습니다.
- **데이터 분석 단위**: OBD 로그 분석 시 15분(900초) 단위로 청크를 나누는 로직이 고정되어 있습니다.
- **대화형 진단 제한**: AI와의 추가 대화 횟수가 3회로 하드코딩되어 있습니다.

### 1.3 소모품 상태 관리 (MaintenanceService)
- **상태 리셋 로직**: 정비 이력 등록 시 무조건 해당 소모품의 잔여 수명을 100%로 갱신하며, 추론 데이터 여부를 `false`로 강제 설정합니다.
- **마스터 데이터 의존성**: 소모품 항목 조회 시 DB에 해당 코드가 없으면 예외를 발생시키며, 기본 주기 설정이 없을 경우 12개월을 강제 적용합니다.

### 1.4 AI 서버 (Python 기반 서비스)
- **프롬프트 및 모델 설정**: `llm_service.py` 내의 다양한 분석 프롬프트와 모델(`gpt-4o`, `gpt-5`) 설정이 코드에 포함되어 있습니다.
- **결함 카테고리**: `LEAK`, `CORROSION` 등 결함 유형이 코드에 정의되어 있어 새로운 유형 추가 시 코드 수정이 필요합니다.

### 1.5 보안 및 설정 (SecurityConfig)
- **CORS 및 허용 경로**: 특정 API 경로(`api/v1/ocr/**` 등)가 보안 필터 제외 목록에 하드코딩되어 있습니다.

## 2. 세부 개선 계획

### 2.1 OCR 소모품 매핑 동적화
- **내용**: `ConsumableItem` DB 테이블에서 활성화된 모든 코드 리스트를 조회하여 GPT 프롬프트에 동적으로 주입합니다.
- **효과**: 신규 소모품이 DB에 추가되면 코드 수정 없이 즉시 OCR 분석 대상으로 포함됩니다.

### 2.2 설정값의 외부 분리 (@Value 활용)
- **내용**: 세마포어 허용량, 타임아웃, 청크 크기, 대화 제한 횟수 등을 `application.yml` 설정 파일로 분리합니다.
- **효과**: 서버 환경(개발/운영/GPU 사양)에 따라 코드 수정 없이 설정을 변경할 수 있습니다.

### 2.3 AI 모델 및 프롬프트 관리 개선
- **내용**: AI 서버의 모델 설정과 결함 카테고리를 환경 변수 또는 별도 설정 파일로 관리합니다.
- **효과**: 모델 업데이트나 진단 기준 변경 시 유연한 대응이 가능합니다.

### 2.4 비즈니스 로직 유연화
- **내용**: 정비 이력 등록 시 '완전 교체'뿐만 아니라 '단순 보충' 등 상태 반영 수준을 선택할 수 있는 옵션을 추가합니다.

## 3. 향후 로드맵
1. **1단계**: OCR 소모품 리스트 동적 추출 적용 (Immediate)
2. **2단계**: 백엔드 주요 상수 설정 파일 분리 (Next)
3. **3단계**: AI 서버 설정값 및 프롬프트 관리 모듈화 (Future)
